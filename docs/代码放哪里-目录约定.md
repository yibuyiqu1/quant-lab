# 代码放哪里：目录约定与理由

> 一句话答案：**你自己的练习代码写在 `src/` 里，文件名加 `my_` 前缀；探索性分析写在 `notebooks/`。**
> 两者都从项目根目录运行，不建额外的包目录。

---

│   ├─ quantlib.py                  ← 工具库（全项目共用，会长期演进）

## 二、为什么是 `src/` 而不是别的地方

| 候选位置 | 结论 | 理由 |
|---|---|---|
| **`src/`** | ✅ **推荐** | 与参考实现、工具库、测试放一起，方便对照；命名 `my_` 前缀不会覆盖任何东西；一个目录找代码，心智负担最低 |
| 项目根目录 | ❌ 不要 | 根目录会被脚本、配置、报告淹掉；`ROOT` 路径计算也会变得不一致 |
| `data/` | ❌ 不要 | 数据目录要能随时删掉重新下载，混进代码会不敢删 |
| `docs/` | ❌ 不要 | 那是笔记和文档的地方 |
| 资料库/ | ❌ 不要 | 只读的资料区，和可执行代码分离 |
| `notebooks/` | ⚠️ 只放探索 | 见下面第四节 |
| `tests/` | ⚠️ 现在还不用 | 项目大了才拆出去；现在 `src/test_*.py` 够用 |
| 新建 `practice/` | ❌ 不必要 | 会多一个目录层级，且要额外处理 import 路径 |

**不推荐的深层原因（很重要）**：Python 找模块靠 `sys.path`，而运行 `python src\xxx.py` 时，被加进 `sys.path` 的是 **`src\` 这一层**。所以：

```python
# src\my_d01_data.py 里这样写是对的：
from quantlib import load_index_returns      # ✅ quantlib.py 就在同一个 src\ 下

# 如果你把文件放到 practice\ 子目录，就得额外折腾路径：
from src.quantlib import ...                 # ❌ 会报 ModuleNotFoundError
```

**保持所有代码在 `src\` 同一层，能让你永远不用思考 import 路径问题**——这对新手是巨大的减负。

## 三、手写练习的两种做法（选一个，别混）

**做法 A：直接改参考文件（推荐给"想被测试自动判分"的人）**

测试认的是 `src/d01_analysis.py` 里的 5 个函数。你可以把函数体清空、自己重写：

```powershell
# 先把参考实现备份一份，随时能对照
Copy-Item src\d01_analysis.py src\ref_d01_analysis.py

# 然后编辑 src\d01_analysis.py：只留函数签名和 docstring，函数体自己写
# 写完验收：
.venv\Scripts\python.exe -m pytest src\test_d01_analysis.py -v
```

**做法 B：另建 `my_` 文件，测试时指定模块名（推荐给"想保留两份"的人）**

骨架已经给你了：[src/my_d01_data.py](../src/my_d01_data.py)（抓数据）和 [src/my_d01_analysis.py](../src/my_d01_analysis.py)（4 个核心函数 + 5 个 TODO）。

测试支持通过环境变量切换检查目标：

```powershell
# 检查你的练习文件（PowerShell 写法，注意分号）
$env:D01_MODULE="my_d01_analysis"
.venv\Scripts\python.exe -m pytest src\test_d01_analysis.py -v

# 检查参考实现（默认行为）
Remove-Item Env:\D01_MODULE
.venv\Scripts\python.exe -m pytest src\test_d01_analysis.py -v
```

测试第一行会打印 `[测试目标] 正在检查模块: xxx`，**跑之前先确认它检查的是你想验的那个文件**。
（我已实测：默认目标 14 全绿；切到骨架文件会全红并提示 `NotImplementedError`，这正是你开始动手的状态。）

**结论**：
- 想省事、想让测试自动判分 → **做法 A**（直接改 `src/d01_analysis.py`）
- 想保留参考实现作对照 → **做法 B**（写 `src/my_d01_analysis.py` + 设 `D01_MODULE`）

## 四、脚本 vs Notebook 的边界（很多人在这里乱）

| | `.py` 脚本（放 `src/`） | `.ipynb` 笔记本（放 `notebooks/`） |
|---|---|---|
| 适合 | 最终结论、可复用函数、需要反复运行的流程 | 探索阶段：不确定要算什么、想看中间结果 |
| Git 友好度 | 好（改动一目了然） | 差（JSON 格式，diff 很难看，容易冲突） |
| 可复现性 | 强（一键重跑） | 弱（容易忘记执行顺序，结果与代码不一致） |
| 能否被测试 | 能 | 不能 |

**规则**：**探索用 notebook，定稿必须回落到 `.py`**。
比如"试了 20 种动量窗口哪个好"用 notebook 很快；一旦确定了 20 日动量，
就把那段写成 `src/quantlib.py` 里的 `momentum(close, window=20)` 函数。

**notebook 路径写法与脚本不同**（因为 notebook 没有 `__file__`）：

```python
# notebook 里用这个（假设在项目根目录启动 jupyter）
from pathlib import Path
ROOT = Path.cwd()          # notebook 的工作目录通常就是启动目录
# 如果 notebook 在 notebooks/ 下启动，就写 Path.cwd().parent
```

## 五、命名规范（面试官真的会看）

| 类型 | 规范 | 例子 |
|---|---|---|
| 变量 | 小写下划线 | `close_price`、`ann_vol` |
| 函数 | 小写下划线，动词开头 | `load_returns()`、`calc_drawdown()` |
| 常量 | 全大写 | `ROOT`、`SEED`、`ANNUAL` |
| 类 | 驼峰 | `BacktestEngine` |
| 文件名 | **全小写 + 下划线，用英文** | `my_d01_data.py` |

**为什么文件名不要用中文**：Windows 下中文路径在 Git、部分库（尤其 C 扩展）、
远程服务器之间经常出编码问题。中文只放在**注释和文档**里，文件名用英文。

**日期前缀是好习惯**：`d01_`、`d02_` 让文件按学习顺序自动排列，
三个月后你一眼能看出"哪天做了什么"。

## 六、什么时候才需要建包（`__init__.py`）

现在**不需要**。当你的项目长到这样时才考虑：

```
src/
├─ data/          ← 子目录，需要 __init__.py
│   ├─ __init__.py
│   └─ loader.py
├─ factors/
│   ├─ __init__.py
│   └─ momentum.py
└─ backtest/
    ├─ __init__.py
    └─ engine.py
```

那时从项目根目录运行：`python -m src.factors.momentum`（注意 `-m` 而不是直接给路径）。
**90 天计划内你到不了这个复杂度**，先别折腾。

## 七、一页总结

1. **练习代码放 `src/`**，文件名 `my_` 前缀或直接改 `d01_analysis.py`。
2. **探索放 `notebooks/`，定稿回落到 `src/` 的 `.py`**。
3. **所有命令从项目根目录执行**，用 `.venv\Scripts\python.exe` 显式调用解释器。
4. **数据/报告/笔记/资料各自分开**，不要把代码混进去。
5. **文件名用英文小写下划线**，中文只写在注释里。
6. **不要建子目录分层**，Python 的 import 路径会让你踩坑。
